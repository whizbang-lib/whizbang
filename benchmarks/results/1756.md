# #1756: hot-path logging, frozen lookups and striped counters, measured

Every candidate in #1756 was measured with BenchmarkDotNet before anything changed. A candidate ships only
where its numbers show a gain; one whose numbers show it does not matter is closed out with those numbers.

| Candidate | Outcome |
|---|---|
| 1. Per-message logging that is always evaluated | **Changed.** Two paths converted; 0 bytes with debug off, locked in by allocation tests |
| 2. Frozen lookups (and the key each lookup builds) | **Changed.** Wire-name key no longer copied; the two by-name tables read per message are frozen |
| 3. Striped counters | **Closed out.** No counter is written often enough for contention to show |

Every `LogDebug`, `LogTrace` and `LogInformation` call in `src/Whizbang.Core`, `src/Whizbang.Transports.AzureServiceBus`
and `src/Whizbang.Transports.RabbitMQ` that takes arguments and is not behind an `IsEnabled` check was listed, then
read in place:

| Where | Runs | Finding |
|---|---|---|

### Tests

- `tests/Whizbang.Core.Tests/Tags/DispatcherTagProcessingLoggingTests.cs`: each of the four paths through tag
  processing allocates 0 bytes over 1,000 calls with debug off, and each still logs its message with debug on. A
  processor that finishes later is awaited before the step completes, and one that fails (already, or later) reaches
  the caller with its own exception.

The step also had to stop being an `async` method on its common paths: in a Debug build the compiler emits the async
state machine as a class, so every call allocated 96 bytes before any logging ran, and the 0-byte guard could not
hold. It now completes synchronously unless the processor does not, and only that case goes through an async helper.
In Release this removes nothing measurable (the state machine is a struct there); it is what lets the guard test hold
in the configuration CI runs.
- `tests/Whizbang.Core.Tests/Workers/PerspectiveWorkerBatchCompositionLoggingTests.cs`: the batch description
  allocates 0 bytes with debug off for a 16-group batch, and still describes every group with debug on.

## 2. Frozen lookups

### Which tables

| Table | Read | Entries | Today |
|---|---|---|---|
| `JsonContextRegistry` wire-name map | every `GetTypeInfoByName`, i.e. every deserialization by name (a message is parsed many times in its life, see #1697) | one per registered message type | `ConcurrentDictionary<string, …>` |
| `ControlPlaneTypeRegistry` names | every received row, and the dead-letter decision | about a dozen | `ConcurrentDictionary<string, bool>` (ordinal) |
| `DispatchPolicyRegistry` | every dispatch | built-ins are already an array indexed by id; only custom policies use a dictionary | not changed |
| The per-type traits table for central dispatch policy (#1395) | | not built yet | nothing to freeze |
| `MessageTagRegistry` and the other `AssemblyRegistry<T>` chains | per dispatch | a short ordered list of generated contributors, not a table | not a lookup table |

Both changed tables stay open for registration for the life of the process (a module initializer runs when its
assembly first loads, which can be after the first message). So the frozen copy is a snapshot: every registration
drops it under a lock, and the next lookup rebuilds it under the same lock. Its construction cost is paid once per
late registration, not once per process.

What the numbers say:

- **Lookup**: frozen is about 3 times faster than the `ConcurrentDictionary` (4.2 ns against 12.6 ns at 16
  entries; 4.8 ns against 15.0 ns at 512). A plain `Dictionary` is no faster than the concurrent one.
- **Construction**: a frozen table costs more to build (57 µs against 20 µs at 512 entries). The extra 37 µs is
  repaid by the 10 ns saved per lookup after about 3,700 lookups, which is a few hundred messages at the parse counts
  measured in #1697. A rebuild happens only when a registration arrives after a lookup, which is a handful of times
  per process.
- **The key**: building the key cost more than the lookup itself. `NormalizeTypeName` copied every name through a
  `StringBuilder`, 384 bytes and about 80 ns for a 70-character wire-form name, even though the wire form the
  framework stores ("Type, Assembly") has nothing to strip. That copy is the bigger cost on this path.
- **Span lookup**: for a fully assembly-qualified name, slicing off ", Version=…" and looking up the slice with
  `GetAlternateLookup<ReadOnlySpan<char>>()` costs 15 ns and nothing allocated, against 129 ns and 496 bytes.
  It was **not adopted**: the framework writes the wire form, not the fully qualified form, so after the wire-form fix
  the common case allocates nothing already; and the slice is exact only for non-generic names (normalization also
  strips metadata inside generic arguments), so it would need a second, span-based normalizer to stay correct.

### What changed

- `EventTypeMatchingHelper.NormalizeTypeName` returns its input when the name contains no "Version=", since only a
  ", Version=" segment starts the stripping. The wire form is now returned as it is.
- `JsonContextRegistry.GetTypeInfoByName` and `ControlPlaneTypeRegistry.IsControlPlane` read a frozen snapshot of
  their tables, rebuilt after a late registration.

## 3. Striped counters

### Survey

There are 50 `Interlocked.Increment`/`Add`/`Decrement` calls in `src/` (outside `Whizbang.Testing`). Sorted by how
often they are written:

| Written | Counters |
|---|---|
| Once per poll, batch, scan, tick or cycle | `ClaimWorker` (all 7), `DeadLetterRecoveryWorker` (all 7), `PerspectiveWorker` (2), `BackupTickCoordinator` (3), `IntegrityAuditWorker`, `TransportDeadLetterDrainWorker`, `PgCommitOrderStamperWorker`, `ClaimChurnFeedback`, `WorkCompletionMeter`, `SignalBusLivenessState`, `ScheduleTimer` |
| Once per registration, connection or subscription | `JsonContextRegistry` (3), `RabbitMQChannelPool`, `AzureServiceBusTransport`, `PgRoleElector`, `WorkCoordinatorGate` |
| Once per message, possibly from several threads | `ReceivedOriginStampMonitor` (per received row), `BatchFlusher` (per enqueued item), `OutboxDrainWorker` (per published message in a parallel drain), `StreamRateLimiter` (per call), `BaseUpsertStrategy` (per recovered duplicate key) |
| Per message, but the value is read back and must be exact | `EmissionIdentity` and `InMemorySequenceProvider` (sequence numbers), `EnvelopeRegistry` and `PolicyContextPool` (pool sizes), `InboxChannelWriter` (held bytes, read for back-pressure). A striped counter cannot serve these: its read is a sum over every slot |

The per-parse diagnostics from #1697 (`MessageParseDiagnostics`) keep no shared counter: an unobserved parse costs
one volatile read, and the recorder used by tests appends to a queue.

The issue suggested `dotnet-trace --clrevents contention`. That event reports `Monitor` lock contention, and
`Interlocked` operations never take a lock, so it cannot see cache-line contention on a counter. The benchmark below
measures it directly instead.

### Outcome: closed out, not changed

Contention is real when every core increments the same counter every few hundred nanoseconds: at 10 threads and
about 225 ns of work between increments, the shared counter doubles the cost. It disappears once the work between
increments reaches about 1.5 to 2 µs: the shared and striped rows are within the run's error. No W! counter comes close
to the contended rate. The busiest are written once per message, and the cheapest whole dispatch measured here, an
in-process invoke with no I/O, already costs 1.3 µs; a message that reaches a counter in the workers has also crossed a
database or a transport. Introducing a striped counter would add a type and a summing read for no measurable gain,
so none was added.
