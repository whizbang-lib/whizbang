# Plan: route every event/payload deserialization through the JSON type registry

## Status: IN PROGRESS — Tier 2a first

## Why

`JsonContextRegistry` (`src/Whizbang.Core/Serialization/JsonContextRegistry.cs`) is the
AOT-safe, source-generated type registry: contexts self-register via `[ModuleInitializer]`,
`CreateCombinedOptions()` chains the resolvers, and `GetTypeInfoByName(name, options)` resolves
a stored type-name string to `JsonTypeInfo` using the canonical
`EventTypeMatchingHelper.NormalizeTypeName`. It is the "advanced and important architecture"
every read path must share.

Audit (verified against source, branch `feature/event-upcasting-rfc`) found the registry is
mostly reached for **event payloads** but the surrounding **type-name → Type resolution** is
hand-rolled and duplicated, and two paths bypass the registry entirely. Divergent resolution =
the same stored event materializing differently depending on which read path / store / transport
read it. That is the worst class of ES bug and it also blocks a single clean upcasting seam
(see `docs/design/event-upcasting.md`).

## Verified findings

### Canonical registry
- `JsonContextRegistry.GetTypeInfoByName(string, JsonSerializerOptions)` → normalizes via
  `EventTypeMatchingHelper.NormalizeTypeName`, looks up `_typeNameMappings`. AOT-safe.
- `JsonContextRegistry.CreateCombinedOptions()` → the combined resolver chain + WhizbangId converters.
- Per-assembly `PerspectivePersistenceJsonContext.CreateOptions(...)` (generated by
  `PerspectivePersistenceJsonContextGenerator`) is the source-gen options used to (de)serialize
  perspective **model** rows; wired as `BaseUpsertStrategy.PathOnePersistenceOptionsProvider`.

### Real problems (fix)
1. **Snapshot ser/deser bypasses the registry [AOT bug].**
   `PerspectiveRunnerTemplate.cs:1142-1146` — `ToSnapshotJson`/`FromSnapshotJson` use raw
   `JsonSerializer.SerializeToDocument(model)` / `Deserialize<TModel>(...)` with **no options**.
   Relies on the reflection resolver (violates L19). Must use the same source-gen options the
   model is persisted with (`PathOnePersistenceOptionsProvider`), exposed via a Core seam since
   the generated runner cannot reference `BaseUpsertStrategy` (EFCore.Postgres) directly.
2. **Event-store polymorphic type-name → Type resolution duplicated 3–4 ways, divergent keys.**
   - `EFCoreEventStore.ReadPolymorphicAsync` — 4-key map (`TypeNameFormatter.Format`, AQN,
     FullName, Name) + `_resolveConcreteType`.
   - `EFCoreEventStore.DeserializeStreamEvents` → `_buildEventTypeLookup` — 4-key.
   - `EFCoreEventStore._getEventsBetweenPolymorphicCoreAsync` — **2-key** (FullName/Name) +
     inline comma-normalization.
   - `DapperEventStoreBase._buildTypeLookup` / `_normalizeEventTypeName` — 2-key, pre-resolved.
   None use `EventTypeMatchingHelper`/registry. Consolidate onto one canonical resolver.
3. **PerspectiveRunnerTemplate snapshot** is the only event/model read that has zero registry path.

### Already correct (verify + lock with tests, do not rewrite)
- Transports: `RabbitMQTransport`, `AsbReceiveDecisionMaker` resolve via `BodyClaimWireHelper`
  / `JsonContextRegistry.GetTypeInfoByName`. (ASB has a `typeBinder.Bind` fallback RabbitMQ lacks —
  note + reconcile.)
- Workers: `InboxDrainWorker`, `OutboxDrainWorker` use `_jsonOptions.GetTypeInfo(...)`.
- `BodyClaimRehydrator`, `Dispatcher._serializeToJsonEnvelope`, `JsonMessageSerializer`,
  `DapperRequestResponseStoreBase`, work coordinators — all already on `_jsonOptions`/registry.

### Benign-by-design (document, leave)
- EFCore reads use `record.Metadata` (EF owned-type mapping) for envelope metadata while drain
  uses `_jsonOptions` for `EnvelopeMetadata`. Different mechanism, same shape. Confirm parity
  with a test; do not force-converge unless the test shows drift.
- InMemoryEventStore holds live objects — no JSON path. Out of scope.

## Shared-seam design

`Whizbang.Core/Messaging/EventTypeMatchingHelper` gains the single canonical resolver:

```csharp
// One normalized strategy. Replaces every hand-rolled typeMap + inline normalizer.
public static bool TryResolveType(string storedTypeName, IReadOnlyList<Type> candidates, out Type resolved);
// (and/or) public static Dictionary<string,Type> BuildLookup(IReadOnlyList<Type> candidates);
```

Semantics preserved from the stores: resolution is **scoped to the perspective's candidate
`eventTypes`** (unknown stored type → skip), but normalization is the one canonical
`NormalizeTypeName` form on both sides. Envelope *assembly* stays per-store (EF record vs raw
row vs Dapper `EventRow` are legitimately different) — only type resolution + options are unified.

Snapshot seam: add a Core-level `static Func<JsonSerializerOptions>?
PerspectiveModelSerializerOptionsProvider` (mirroring `PathOnePersistenceOptionsProvider`,
set by the same `[ModuleInitializer]` callback), read by the generated runner's snapshot helpers.
