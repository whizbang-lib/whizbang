## #2548 inventory

How it was found: WHIZ607 already routes every type-name read in `src/` through the shared naming code
(`TypeNameFormatter`, `EventTypeMatchingHelper`, the types marked `[TypeNameAuthority]`). WHIZ610 reports a call to that
code whose result reaches a log call at `Information` or below (or an `ActivitySource.StartActivity` name) outside an
`IsEnabled` (or `HasListeners`) check. A first build with the rule as a warning reported 20 log sites; the dispatch
activity sites and the stream id report were found by reading the per-message paths for consumers that are not log
calls.

Not changed, with the reason:

- `RabbitMQTransport` receive diagnostics: already behind `_logger?.IsEnabled(LogLevel.Debug) == true`; WHIZ610 learned
  that shape.
- `PerspectiveRunnerBase` (`_tryResurrect`, `_applyAlone`), `PerspectiveRebuilder.LogRebuildEventNotPublished`,
  `ReceptorInvoker.LocalStageRanWithoutContext`: inside a `catch` clause. The read happens only after an exception was
  thrown, which costs far more; WHIZ610 does not report a read in a catch clause.
- `MessageTagProcessor`, the cascade's other debug logs, `Dispatcher.ExtractingResponse`: already guarded.
- `Activity?.SetTag(..., TypeNameFormatter...)`: the activity is null when nothing listens, so the null-conditional
  call never evaluates its arguments.
- Warnings and errors (`StreamIdInheritanceRefused`, once per pair of types, and others): on in production and on rare
  paths; not reported by WHIZ610.

Found while measuring, not in scope (follow-up candidate): `ReceptorInvoker`'s owned-domain filter reads the message
type's namespace (`TypeNameFormatter.NamespaceOf`) on every PreOutbox stage once owned domains are configured. The
runtime keeps `Type.Namespace` in the same weakly held cache as `Type.Name`, so that read rebuilds the cache after every
collection (measured: 168 bytes per collection, even for a type in the global namespace). It is the filter's own
functional read, not a log's, so it is outside #2548; the owned-domain allocation test measures that read alone and
takes it off. A per-type cache of the ownership answer, or of `NamespaceOf`, would remove it.

### Test technique

`WeakNameCacheProbe.ExtraBytesAfterCollections` (shared helper, `tests/Whizbang.Core.Tests/Helpers`) runs a call 25
times with a full collection before each run and 25 times without; the difference is what the collections cost it.
The paths under test allocate for other reasons (a list, a state machine), so the #2535 form (zero bytes with one
collection in the window) could not be used everywhere; the differential is zero on the fixed code and positive on
every run of the old code, independent of timing. Paths that otherwise allocate nothing (`ValidateAppend`,
`StartDispatch`) use the #2535 form directly.

## Guard (#2548)

WHIZ610 (`tools/Whizbang.RepoAnalyzers/EagerLogTypeNameAnalyzer.cs`), an error in `src/` and off elsewhere
(`TypeNaming.OutsideLibrary.globalconfig`). It is library-wide rather than limited to "hot paths": which methods are
per-message is not something the code states, so a list of them would rot, while the rule costs a startup log one
`IsEnabled` check.

Where it is not precise, and what covers the gap:

- Consumers it recognizes: `[LoggerMessage]` methods, `LoggerExtensions.LogTrace/LogDebug/LogInformation/Log`,
  `ILogger.Log`, and `ActivitySource.StartActivity/CreateActivity`. A type name passed to another method that only logs
  it (the stream id report took the name as a string) is not seen: no analyzer can know what a callee does with a
  string. The stream id report now takes the `Type`; this is the case the plan records as not guardable precisely.
- A local is followed only when every read of it is a log argument (a name also used for an exception or a key is a
  functional read).
- Checks it recognizes: `IsEnabled`/`HasListeners` calls (also `x?.IsEnabled(...) == true`), a local `bool`
  initialized from one, conjunctions, the then-branch of an `if`, the true arm of `?:`, the right side of `&&`, and an
  earlier `if (!...IsEnabled(...)) return/throw/continue/break;`. A check behind a helper property is not seen and is
  reported (fails safe).
- Reads inside a `catch` clause are not reported.

## #2549 design

- `GuidOrderingValidator.ReportStreamId(Guid streamId, string messageType, string entryPoint)`: a v7 or empty stream id
  returns at once (no lookup). Otherwise the stored name is resolved through `JsonContextRegistry.TryGetTypeByName`
  (new, internal): the name map the generated JSON contexts register in module initializers, the same lookup
  `GetTypeInfoByName` makes on every inbox deserialization, without building metadata. No reflection. The type's
  `[StreamId]` type comes from `StreamIdExtractorRegistry.GetStreamIdType` (generated), so an `AcceptAnyVersion` strong
  id is never reported. A name that does not resolve gives no stream id type, so the id is reported, not skipped.
- EF Core and Dapper `_serializeNewInboxMessages` call it for every message with a stream id, in the loop that already
  refuses non-v7 message ids, before any SQL runs: a refusal at `Error` leaves nothing of the batch.
- Entry points: `EFCoreWorkCoordinator.InboxWrite`, `DapperWorkCoordinator.InboxWrite` (the existing constants).
