## The three chunks

| Chunk | What | Why |
|---|---|---|
| **A. Sane defaults** | `MaxInboxAttempts=10`, `MaxOutboxAttempts=10`, `NotifyHealthyPollingIntervalMilliseconds=30_000` | Today's defaults silently retry forever and poll at 250ms even when NOTIFY is healthy. Operators have to discover this the hard way (we discovered it the hard way today). |
| **B. NOTIFY-first work coordination** | Catch-up on listener reconnect + startup, orphan-detection NOTIFY emission, `ScheduledRetryWorker`, optional `NotifyOnly` mode | Polling exists today as a 250 ms hedge against NOTIFY unreliability. The cases it covers (orphan recovery, scheduled retries, NOTIFY-loss catch-up, startup state discovery) are each individually solvable with NOTIFY + targeted catch-up calls. Polling becomes a true safety net at long cadence. |
| **C. DLQ recovery** | Per `plans/dlq-recovery.md` — two-flow design: transport DLQ + Whizbang internal `wh_dead_letters` table. Idle-cadence trigger, generation-tagged auto-replay on deploy, per-reason policy, operator API. | The dead-letter mechanism the defaults activate (chunk A) needs a partner: recovery. Otherwise we just trade "retries forever" for "permanently failed" with no path back. |

Each chunk has its own slice list below. Slices marked `[done]` ship in order; this plan is updated as work lands.

## A. Sane defaults

### A.1 `InboxDispatchWorkerOptions.MaxInboxAttempts`

- Today: `int? MaxInboxAttempts { get; set; }` — default `null`, dead-lettering disabled.
- Fix: `int? MaxInboxAttempts { get; set; } = 10;`
- Migration concern: applications that DIDN'T set this and DID rely on infinite retries lose that. Document in CHANGELOG; the new default is a safer floor.

### A.2 Outbox max attempts — DEFERRED to chunk C

There's no worker-level `MaxOutboxAttempts` option today. `OutboxDrainWorker` / `OutboxPublishWorker` don't dead-letter at all; the `attempts` column on `wh_outbox` accumulates without bound. Adding dead-letter machinery here requires it to land alongside the uniform `wh_dead_letters` route in chunk C (otherwise we'd build a status-bit-only DLQ for outbox now and immediately rewrite it in chunk C).

→ Defer outbox dead-lettering to slice C.4 (FailureFlushWorker integration).

### A.3 Perspective-events max attempts — DEFERRED to chunk C

Same situation as outbox. `wh_perspective_events.attempts` increments per `claim_orphaned_perspective_events` but no worker-level limit fires. Falls into chunk C's uniform wiring.

→ Defer to slice C.4.

### A.4 `ClaimWorkerOptions.NotifyHealthyPollingIntervalMilliseconds`

- Today: `int? NotifyHealthyPollingIntervalMilliseconds { get; set; }` — default `null` (use tight 250 ms baseline).
- Fix: `int? NotifyHealthyPollingIntervalMilliseconds { get; set; } = 30_000;`
- Behavior: when gate.IsAvailable=true, baseline is 30 s; when gate flips false, immediately reverts to `PollingIntervalMilliseconds` (250 ms).

### A.5 Tests

- Verify each new default with `Options.Create(new XOptions())` and assert the field.
- Verify behavior contract: with the new defaults, an inbox row with `attempts > 10` dead-letters on the next claim.

## B. NOTIFY-first work coordination

### B.1 Catch-up on listener reconnect

When `INotifySignalingGate` transitions `IsAvailable: false → true`, fire a one-shot `claim_orphaned_outbox + _inbox + _perspective_events` to drain anything that accumulated during the unavailable window.

- Hook lives in `ClaimWorker._onGateAvailabilityChanged` (already called on transition; today only calls `RequestImmediatePoll()`).
- Replace: when `nowAvailable && _wasUnavailableForAtLeastNms`, fire an explicit catch-up call.
- "At-least-N-ms" guards against rapid flapping triggering a storm.

### B.2 Catch-up on startup

Same idea: on `ExecuteAsync` first iteration, regardless of NOTIFY state, fire one explicit `claim_orphaned_*` to discover pre-existing pending work. Then enter the normal loop.

### B.3 Orphan-detection NOTIFY emission

Today `cleanup_stale_instances` (mig 011) DELETEs dead-instance rows. After the DELETE, emit `pg_notify('wh_work_i_<remaining_instance_ids>', 'orphan')` so each live instance fires a catch-up claim.

- Implementation: add `PERFORM pg_notify(...)` lines in `cleanup_stale_instances` SQL.
- Per-instance channel naming matches existing `wh_work_i_<id>` convention.
- Receivers: `PgWorkNotificationListener.OnNotification` adds an `"orphan"` payload case → triggers a one-shot `claim_orphaned_*` call.

### B.4 `ScheduledRetryWorker` — low-cadence NOTIFY emitter

New worker. Polls only the narrow case "rows whose scheduled_for time has passed":

```sql
SELECT DISTINCT stream_id FROM wh_outbox
WHERE processed_at IS NULL AND scheduled_for <= NOW() AND scheduled_for IS NOT NULL
UNION
SELECT DISTINCT stream_id FROM wh_inbox
WHERE processed_at IS NULL AND scheduled_for <= NOW() AND scheduled_for IS NOT NULL
-- (no wh_perspective_events scheduled_for in current schema; if added, include)
```

For each found stream_id, emit a `pg_notify` so the regular drain path picks it up.

- Cadence: `ScheduledRetryWorkerOptions.PollIntervalSeconds = 10` (configurable; 5-30 range).
- Doesn't compete with `ClaimWorker` for work — it only emits NOTIFYs, doesn't claim.
- Cost: one cheap indexed query every 10 s. Vastly less than `claim_work` at 4 Hz.

### B.5 `WorkSignalingMode.NotifyOnly` mode

Today: `WorkSignalingMode { ListenNotify, Polling }` (or similar). Add a third: `NotifyOnly` which:

- ClaimWorker's adaptive backoff is allowed to grow without bound (no safety-net poll at all)
- The 30 s safety net only kicks in if gate.IsAvailable flips false
- Effectively: zero polling when NOTIFY is healthy and signaling-mode is NotifyOnly

This is the "I trust my NOTIFY connection" mode for environments where the operator has confirmed direct connection is solid.

Default: still `ListenNotify` (hybrid) for back-compat. Operators opt into `NotifyOnly`.

### B.6 Tests

- Reconnect catch-up: arrange gate-flip false→true; assert claim_orphaned_* invoked exactly once.
- Startup catch-up: arrange existing wh_outbox rows; start worker; assert immediate claim before any NOTIFY signal.
- Orphan NOTIFY: dead-instance scenario; assert `cleanup_stale_instances` emits orphan NOTIFY; assert `PgWorkNotificationListener` routes it to ClaimWorker.
- ScheduledRetryWorker: row with `scheduled_for <= NOW()` and `processed_at IS NULL`; assert NOTIFY emitted; assert no UPDATEs to the source table.
- NotifyOnly mode: gate healthy + no signals; assert claim_work call rate approaches zero over time (vs the hybrid mode's 30 s floor).

## C. DLQ recovery

Full implementation per `plans/dlq-recovery.md` (already designed, all 5 design questions resolved).

### C.1 SQL migration — `wh_dead_letters`

Schema per the design doc. Includes:
- Identity + source pointer + envelope + metadata
- failure_reason, error_text, attempts_when_dlq, dead_lettered_at, dead_lettered_by
- recovery_status, recovery_attempts, last_recovery_at, next_recovery_at, recovered_at
- generation, retried_on_generations (text array)
- operator_disposition, operator_notes, operator_actor

Plus indexes per design (next_recovery_at, stream_id, generation).

New atomic SQL function `move_to_dead_letters(source_table, source_id, instance_id)` that:
- Inserts the row into wh_dead_letters with full forensic snapshot
- Deletes from source table
- Returns the new dead_letter_id

### C.2 `DeadLetterEntry` record + `IDeadLetterStore` interface

In Whizbang.Core/Messaging or similar.

### C.3 EFCore + Dapper `IDeadLetterStore` implementations

### C.4 `FailureFlushWorker` integration

When attempts exceeds threshold, route to `IDeadLetterStore.AppendAsync` instead of just setting status bit.

### C.5 `DeadLetterRecoveryOptions` + `RecoveryPolicy` types

Per the design doc's policy matrix:
- Throttled → AggressiveRetry (3 × 30 min)
- TransportException → MediumRetry (3 × 1 hr)
- LeaseExpired → AggressiveRetry (5, immediate)
- MaxAttemptsExceeded → ConservativeRetry (1 × 6 hr)
- EventStorageFailure → HoldForReview
- ValidationError → HoldForReview
- SerializationError → HoldForReview
- TransportNotReady → MediumRetry (3 × 30 min)
- Unknown → OneShotRetry-then-Hold

### C.6 `IDeadLetterRecoveryPolicy` interface + default impl

Hybrid: default reads `[StreamRecovery]` attribute on perspectives + `[FifoStreamRecovery]` on event types. Application can replace whole policy.

### C.7 `DeadLetterRecoveryWorker`

- Scan loop on idle-cadence triggers (timer backstop 10 min + IWorkCoordinator.OnBatchEmpty + generation transition + operator API)
- Generation replay first (highest priority)
- Operator-requested retries (RetryNow disposition)
- Cooldown-driven retries
- Stream-aware grouping via IDeadLetterRecoveryPolicy
- Re-emit: mark Recovering, INSERT back into source table with attempts=0
- Track recovery outcome; update wh_dead_letters status accordingly

### C.8 Transport DLQ recovery — Subscribe mode

Configurable via `TransportDlqRecoveryOptions.Mode` (default `Subscribe`):
- ASB: `ServiceBusReceiverOptions { SubQueue = SubQueue.DeadLetter }`
- RMQ: bind Whizbang-managed consumer to DLX

Pulls from broker DLQ, re-publishes to main subscription. After N failures, escalates to internal DLQ.

### C.9 Transport DLQ recovery — Poll mode

Per-poll receivers, no extra long-lived connections. Operator falls back here for connection-budget-constrained environments.

### C.10 Operator API in `Whizbang.Hosting.AspNet`

```
GET    /dlq                    — paginated list with filters
GET    /dlq/{id}               — full forensic detail
POST   /dlq/{id}/retry         — set disposition=RetryNow
POST   /dlq/{id}/hold          — set disposition=HoldIndefinitely
POST   /dlq/{id}/give-up       — set status=PermanentlyFailed
POST   /dlq/bulk/retry         — body: { filter, max_count }
POST   /dlq/scan-now           — trigger immediate worker scan
GET    /dlq/stats              — counts by reason/status
```

Opt-in via `AddWhizbangDeadLetterApi()`.
