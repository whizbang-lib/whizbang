---
category: Changed
subsection: Storage
---
- **A strong id inside a perspective document is stored as a UUID string, not `{"Value": ...}` (#2518).** On every
  context that carries the Whizbang options extension (every generated perspective context), a `[WhizbangId]` is a
  `uuid` scalar: Entity Framework and the atomic upsert both write it as the UUID string, the same as a `Guid` and as
  the transport writes it, once every live instance reads that form (below), at any depth (nested objects, collection elements, dictionary keys and values, nullable
  ids). This holds for the first model a process builds even when no code of the ids' assembly has run yet: the lookup
  runs that assembly's module initializer. `Contains` over ids now translates, where before it threw. A read-model
  property can change from `Guid` to a strong id with no change to the stored data.
  **The switch waits for the whole fleet.** An earlier release's Entity Framework mapping cannot read the UUID string,
  so each instance announces in its heartbeat that it reads it (`stored_form_level` 2 in `wh_service_instances.metadata`;
  `HeartbeatRequest.STORED_FORM_LEVEL` is now 2). The schema's gate, `wh_strong_id_document_gate`, latches
  `wh_settings` `strong_id_uuid_string_documents` once every live instance does, asked at every start and every
  maintenance cycle; until then both writers keep writing the object form every release reads. Once it is open each
  instance switches its writes (`WhizbangIdDocumentForm`) and announces that too (`strong_id_document_form`), and the
  rewrite starts only once every live instance writes the UUID string, so none writes the object form behind it. What
  an instance announces decides, not its version: two prereleases of one release are told apart. The latch is one-way,
  like the metadata trim gate: an earlier release started after it cannot read rows written since. One package, with
  no ordered pair of releases to deploy.
  Rows an earlier release stored in the object form are rewritten a batch at a time, each batch committed on its own
  under the rewrite's own advisory lock (not the schema lock, so a starting instance's schema pass never waits on a
  slice), with the last primary key it reached recorded in the journal (`strong-id-scalar:<table>:<shape>`
  in `wh_stored_form_migrations`, new columns `resume_key` and `pass_rows_converted`, migration 562). Startup runs one
  slice, within four fifths of the command timeout, and a maintenance step carries on from the recorded key until every
  table settles, so a table of any size finishes and a restart redoes nothing. A table settles on a complete pass that
  converts nothing, which also converts a row written behind the key meanwhile. Until every row is converted, both forms are read: the readers take either and count the old one on
  `whizbang.perspective.identifier_form_fallbacks` (`StoredFormFallbacks.ScalarIdentifierRead` is replaced by
  `ObjectFormIdentifierRead`), and every query that reads an id in SQL (equality, `Contains`, ordering, projection, a
  collection element, a collection of ids, document containment in either containment mode, and the predicates of
  `ExecuteUpdate` and `ExecuteDelete`) matches either form. The document index answers an id equality in both forms.
  **Upgrade:** nothing to change for perspective documents. A strong-id property of your own entity on a context with
  the extension, outside a document, now maps to a `uuid` column named after the property instead of being discovered
  as a complex type; add a migration for it if you have one. Hand-written SQL or containment queries that matched
  `{"Value": "..."}` should match the UUID string instead. A LINQ query on an id's `Value` inside a document
  (`Where(r => r.Data.OrderId.Value == guid)`) no longer translates, because `Value` is not a mapped member of a
  scalar: compare the id itself (`r.Data.OrderId == orderId`). `WhizbangIdProviderRegistry.RegisterValueMember` and
  `GetValueMembers`, which only the GraphQL id filter used to reach `Value`, are removed. A collection of ids in a
  document (`List<TId>`) is stored as an array of UUID strings and `Contains` over it translates on a context with the
  extension; a context without it cannot build a model that holds one. The atomic upsert leaves a null id out of the
  document where Entity Framework writes the key as `null`; both read back, and query, as null.
