---
category: Changed
subsection: Storage
---
- **A strong id inside a perspective document is stored as a UUID string, not `{"Value": ...}` (#2518).** On every
  context that carries the Whizbang options extension (every generated perspective context), a `[WhizbangId]` is a
  `uuid` scalar: Entity Framework and the atomic upsert both write it as the UUID string, the same as a `Guid` and as
  the transport writes it, at any depth (nested objects, collection elements, nullable ids). An id predicate in a
  query translates to `CAST(data ->> 'OrderId' AS uuid) = @p`, and `Contains` over ids now translates, to
  `= ANY (@ids)`, where before it threw. A read-model property can change from `Guid` to a strong id with no change to
  the stored data. Rows an earlier release stored in the object form are rewritten once at startup by the stored-form
  phase (journaled as `strong-id-scalar:<table>:<shape>`, migration 557), before any query runs; until then the readers
  take either form and count the old one on `whizbang.perspective.identifier_form_fallbacks`, which now counts
  object-form reads (`StoredFormFallbacks.ScalarIdentifierRead` is replaced by `ObjectFormIdentifierRead`).
  **Upgrade:** nothing to change for perspective documents. The first startup rewrites each table that stores a strong
  id, in the stored-form phase, so plan for one pass over those tables. A strong-id property of your own entity on a
  context with the extension, outside a document, now maps to a `uuid` column named after the property instead of
  being discovered as a complex type; add a migration for it if you have one. Hand-written SQL or containment queries
  that matched `{"Value": "..."}` should match the UUID string instead.
