---
category: Changed
subsection: Storage
---
- **A strong id inside a perspective document is stored as a UUID string, not `{"Value": ...}` (#2518).** On every
  context that carries the Whizbang options extension (every generated perspective context), a `[WhizbangId]` is a
  `uuid` scalar: Entity Framework and the atomic upsert both write it as the UUID string, the same as a `Guid` and as
  the transport writes it, once every live instance reads that form (below), at any depth (nested objects, collection elements, dictionary keys and values, nullable
  ids). This holds for the first model a process builds even when no code of the ids' assembly has run yet: the lookup
  runs that assembly's module initializer. `Contains` over ids now translates, where before it threw. A read-model
  property can change from `Guid` to a strong id with no change to the stored data.
  **The switch waits for the whole fleet.** An earlier release's Entity Framework mapping cannot read the UUID string,
  so each instance announces in its heartbeat that it reads it (`stored_form_level` 2 in `wh_service_instances.metadata`;
  `HeartbeatRequest.STORED_FORM_LEVEL` is now 2). The schema's gate, `wh_strong_id_document_gate`, latches
  `wh_settings` `strong_id_uuid_string_documents` once every live instance does, asked at every start and every
  maintenance cycle; until then both writers keep writing the object form every release reads. Once it is open each
  instance switches its writes (`WhizbangIdDocumentForm`) and announces that too (`strong_id_document_form`), and the
  rewrite starts only once every live instance writes the UUID string, so none writes the object form behind it. What
  an instance announces decides, not its version: two prereleases of one release are told apart. The latch is one-way,
  like the metadata trim gate: an earlier release started after it cannot read rows written since, and **rolling back
  below this release once the switch has flipped is not supported**. Each check after the latch names any live instance
  below level 2 (a Warning when the set changes, and the `whizbang.perspective.strong_id_unreadable_instances` gauge,
  tagged by instance, service and host), and the rewrite asks the gate before every batch, so such an instance joining
  mid-run stops it. Operators read where a schema stands with `wh_strong_id_document_status()`, which never latches;
  `wh_strong_id_document_unreadable_instances()` lists the instances that cannot read the new form. The form is decided
  per schema: the upsert, collective setters and `ExecuteUpdate` write the UUID string into a schema once its own gate is
  open, whatever the process's other schemas say, and each schema's heartbeat says what this process writes into it. A
  schema with no gate (not yet migrated, or migrated by an earlier release) is held, so nothing writes the UUID string
  into it. A save that writes rows into several schemas writes the UUID string only while every one of their gates is
  open. A schema is known by the name the server gives its database (`current_database()`, asked once per host and
  database name), not the connection string's, so a writer behind a pooler alias such as pgbouncer, or a coordinator
  with a connection string of its own, sees the gate the check opened. Reading the form never takes a lock.
  `ExecuteUpdate` sets an id in the form the fleet reads, decided each time the statement runs, and sets a null id as
  JSON `null`, on a context without the extension too: the generated context's new `OnConfiguring` calls the base
  context's, then `OnConfiguringExtended`, then gives the options the framework's query postprocessor when they lack it.
  A context it cannot reach fails when its model is built, naming the fix: a pooled context without the extension, whose
  options are frozen first, or a hand-written one that calls `WhizbangIdConvention.Apply(modelBuilder, this)` but never
  `WhizbangIdConvention.Configure`. Each rewrite records its statement's content hash (develop's migration 568), so the
  rollback gate judges it by content. One package, with no ordered pair of releases to deploy.
  **The Dapper driver writes the UUID string and reads both forms.** Its store has always written the UUID string with
  Whizbang's options, and the generated id converter read only that, so sharing one perspective table between Entity
  Framework and Dapper instances was not supported before this release: each failed on the other's rows. The converter
  now reads `{"Value": ...}` as well as the UUID string, so every reader on either driver reads both. The Dapper store
  keeps writing whatever its serializer options write, the UUID string with Whizbang's (the gate governs the Entity
  Framework writer, the only one an earlier reader could not follow), and its heartbeat says which from its first beat,
  so a store built with an application's own options, which write the object form, holds the rewrite. It also asks the
  gate at host start and each maintenance cycle.
  Rows an earlier release stored in the object form are rewritten a batch at a time, each batch committed on its own
  under the rewrite's own advisory lock (not the schema lock, so a starting instance's schema pass never waits on a
  slice), with the last primary key it reached recorded in the journal (`strong-id-scalar:<table>:<shape>`
  in `wh_stored_form_migrations`, new columns `resume_key` and `pass_rows_converted`, migration 562). Startup runs one
  slice, within four fifths of the command timeout, and a maintenance step carries on from the recorded key until every
  table settles, so a table of any size finishes and a restart redoes nothing. A table settles on a complete pass that
  converts nothing, which also converts a row written behind the key meanwhile. Until every row is converted, both forms are read: the readers take either and count the old one on
  `whizbang.perspective.identifier_form_fallbacks` (`StoredFormFallbacks.ScalarIdentifierRead` is replaced by
  `ObjectFormIdentifierRead`), and every query that reads an id in SQL (equality, `Contains`, ordering, projection, a
  collection element, a collection of ids, document containment in either containment mode, and the predicates of
  `ExecuteUpdate` and `ExecuteDelete`) matches either form. The document index answers an id equality in both forms.
  **Upgrade:** nothing to change for perspective documents. A strong-id property of your own entity outside a document
  is a `uuid` column named after the property. An id an earlier release mapped as a complex type without configuring
  it (inside a table-split complex type, or on a context without the extension) had the column its `Value` had,
  `Depot_DepotId_Value`, and now has `Depot_DepotId`: run `migrations add`, which scaffolds the move as `RenameColumn`,
  so the values stay. Whizbang's migrations model differ pairs each `<column>_Value` with `<column>` by name, where
  Entity Framework alone would pair two ids of one shape in name order and swap their values; a pair it cannot make by
  name fails `migrations add`, naming the columns. An id you configured (`ComplexProperty`, `HasColumnName`,
  `HasConversion`) keeps what you configured. The rename is a deploy step, not a rolling one: instances of the earlier
  release read the old column and this release reads the new one, so stop the earlier release's instances that use the
  table, apply the migration, then start this release. The generated context now overrides `OnConfiguring`; a partial
  class of yours that overrode it moves its body to the new `OnConfiguringExtended` (WHIZ704 names it). A hand-written
  context that called `WhizbangIdConvention.Apply(modelBuilder)` passes the context, `Apply(modelBuilder, this)`, and
  calls `WhizbangIdConvention.Configure(optionsBuilder)` at the end of its `OnConfiguring`, unless its options call
  `UseWhizbangFunctions()`. Hand-written SQL or containment queries that matched
  `{"Value": "..."}` should match the UUID string instead. A LINQ query on an id's `Value` inside a document
  (`Where(r => r.Data.OrderId.Value == guid)`) no longer translates, because `Value` is not a mapped member of a
  scalar: compare the id itself (`r.Data.OrderId == orderId`). `WhizbangIdProviderRegistry.RegisterValueMember` and
  `GetValueMembers`, which only the GraphQL id filter used to reach `Value`, are removed. A collection of ids in a
  document (`List<TId>`) is stored as an array of UUID strings and `Contains` over it translates on a context with the
  extension; a context without it cannot build a model that holds one. The atomic upsert leaves a null id out of the
  document where Entity Framework writes the key as `null`; both read back, and query, as null.
