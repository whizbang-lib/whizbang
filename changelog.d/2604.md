category: Added
subsection: Context, identity & serialization
---
- **A strong id can derive from the handling it is created in: `OrderId.DeriveFrom(Handling.Current, "order")`
  (#2604).** Every generated `[WhizbangId]` type now has `DeriveFrom(handling, purpose)`. Inside a receptor body it
  returns an id derived from the handled message, the service, the handler, the receptor, the type's pinned id and the
  purpose, so a retry of the handling (a lapsed lease, a completion that never committed) gets the same id instead of
  a new one that nothing else refers to. The id is a UUIDv7 that sorts with the handled message. One id per purpose:
  a second call for the same type and purpose in one handling throws, so name the item in the purpose for a
  collection (`$"line:{sku}"`). Outside a receptor body, or after the body returned, `DeriveFrom` throws and says why;
  `New()` still mints. The derivation input is the type's pinned id, never its name, so a rename or a namespace move
  keeps every id it derives: pin the type with `[PinnedId("<guid>")]` on its struct, or
  `[WhizbangId(PinnedId = "<guid>")]` where it is declared (a property or parameter has no struct to pin). The
  pinned-type ledger records pinned strong ids (kind `strong-id`) and the pinned-id registry maps them. New
  diagnostics: WHIZ118 (error) for a `DeriveFrom` call on an unpinned id, WHIZ119 (error) when a strong id's pinned id
  disappears from the ledger (changing it changes every derived id), and WHIZ123 (error) when declarations of one id
  pin it differently. WHIZ112 now also checks a strong id's pin. **Upgrade:** nothing to change; ids stay unpinned
  until you pin them, and `DeriveFrom` is only needed where you call it.
