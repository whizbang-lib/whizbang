- **A pair guard halt survives a restart, and its history is kept (#2377).** When two services apply different
  integrity rules to an event type they share, the pair guard halts integrity for the pair and alerts once it stays
  halted past `Whizbang:StreamIntegrity:PairGuard:HaltedAlertAfter`. The halt and the time it began were held in memory,
  so a restart reset the alert clock (a service that restarted more often than the alert window never alerted) and lost
  the record of halts and resumptions. Each halt is now kept in `wh_integrity_pair_halts` (migration 531): the peer and
  which end this service is, the reason, the types whose rules differ, both sides' rule versions and fingerprints, and
  when it began, was alerted and resumed. A restarted service loads the open halts before its first verdict, so the
  alert fires on schedule and is not raised twice; several instances of one service share one halt per pair. Resumed
  halts roll off under `Whizbang:OperationalRetention:PairHistory`. The store keeps history only: a store that cannot
  be read or written is logged and the guard carries on in memory. `IntegrityPairGuard.Admit` is replaced by
  `AdmitAsync`, which takes the service's `IWorkCoordinator`. **Upgrade:** code that called
  `IntegrityPairGuard.Admit(peer, side, fingerprint)` calls `await AdmitAsync(coordinator, peer, side, fingerprint)`
  (pass null to keep the state in memory only).
