---
category: Added
subsection: Work coordination, perspectives & sagas
---
- **A perspective declares the rows another stream's event targets, by a key column (#2618).** A perspective
  implements `IPerspectiveFanOutFor<TModel, TEvent>` for an event of another stream: `Targets` names the key with
  `FanOut.By<TModel>(row => row.Key)`, and `Apply` returns the set-based change, as a `[CollectiveApplyFor]` handler
  does. The build reads the key and refuses a declaration it could not run as written: a `Targets` that names no key
  property (WHIZ124), a key that is not a `[PhysicalField]` (WHIZ125), has no `[Indexed]` (WHIZ126) or is not a `Guid`
  or a strongly typed id over one (WHIZ127), and a set-based apply that assigns a fan-out key (WHIZ128). WHIZ106 now
  also holds a fan-out's `Apply` to reading only the row and the event. Each accepted fan-out is registered with its key
  column in the `IPerspectiveFanOutRegistry` the host serves, with nothing to register by hand. The fan-out member is
  `Apply(TEvent)`, as every other member that turns an event into a row change is.
- **A foreign event a perspective fans out updates every row it targets, live, in one set-based statement per batch
  (#2619, #2620).** The startup associations step writes each fan-out event type as a perspective association to the
  collective sink, so both emit chains give the event one sink row with no new statement on the store's hot path, and
  the associations hash covers the fan-out set, so the release that first carries a fan-out runs the standby
  handshake. The sink dispatches the event through the collective dispatcher, scoped to the event's stream and tenant:
  on EF Core and Dapper alike it is one keyset-batched `UPDATE ... WHERE key = stream AND tenant = tenant`, under the
  apply lock and the resumable progress record, so a redelivered event applies once and an interrupted apply resumes.
  A foreign delete marks or clears rows and never removes them. There is nothing to register: the EF Core Postgres
  driver registers the collective dispatcher for a host that declares a fan-out, and the dispatcher makes each fan-out
  model's executor. A host that declares a fan-out it could not apply (no collective dispatcher, or a Dapper host,
  which has no associations step or perspective worker) is refused at startup with the models and the fix in the
  message. A strongly typed id key matches by its Guid. Two more build errors: a fan-out on a type the generated
  registry cannot reach (WHIZ129) and a fan-out of a collective event (WHIZ143). A sink row this build cannot apply is
  completed as before but counted on `whizbang.collectives.unhandled` and named in a Warning. Rebuild and rewind of
  fan-out rows follow in the next slice.
