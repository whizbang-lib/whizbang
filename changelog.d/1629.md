- **Received streams stored out of their origin's order can be re-sequenced in place (#1629).** Before #1607 a
  receiver could store one producer stream's events out of the producer's order. `IReceivedStreamResequencer`
  (registered by both Postgres drivers) finds such streams and stores each origin's events in that origin's order,
  in the versions those events already hold; local events, and the interleaving of different origins, keep their
  versions. The order is the one a replay already folds (`ReplayEventOrder`), so reads by version and replays now
  agree. Each re-sequenced stream's snapshots are removed and its perspectives are flagged to rewind from the stream's
  start (migration 555). The run walks the store in bounded batches, takes no lock it would wait for (a stream being
  written is reported busy), checks every planned event is still where it was read, and can be repeated or resumed;
  a dry run changes nothing and reports what it would. Streams with ephemeral or collective events, or archived
  history, are reported and left alone. Audit records keep the stream position they recorded. Nothing to change; run
  it once (dry run first) on a receiver that stored events before the #1607 fix.
