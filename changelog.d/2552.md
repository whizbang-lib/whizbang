---
category: Changed
subsection: Context, identity & serialization
---
- **A `[GenerateStreamId]` event invoked locally inside a receptor's handling now starts a stream derived from the
  handling (#2552).** Before, `LocalInvokeAsync` minted a fresh stream for it even inside a handling, so a redelivered
  handling started a second stream that nothing else referred to, while sent commands (#2537) and published events
  (#2274) already derived theirs. The void local invoke builds no envelope, so the event has no id to derive from;
  its stream derives from the handling instead, as a sent command's does, on ordinals of the handling's own for
  invoked events. Invoking such an event therefore does not change the streams of the commands the handling sends,
  nor the ids of the events and commands it emits. The same instance invoked twice keeps its stream, and outside a
  receptor (an API endpoint, a background service) each event still mints a fresh stream, with no added allocation on
  the void path. Also fixed: a published `[GenerateStreamId]` event with a local receptor, in a host with the
  envelope registry (any host built with `AddWhizbang`), handed its local receptors a second, freshly minted stream
  instead of the one derived from the event's id that the stored copy and the delivery receipt carry; one publish now
  gives the event one stream everywhere it goes. **Upgrade:** nothing to change in code. A handling whose first run
  happened before the upgrade and is redelivered after it starts the invoked event's stream once more, as before.
