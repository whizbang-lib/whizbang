category: Changed
subsection: Storage
---
- **An archive location mismatch is handled as configured, and the location pin is stored normalized (#2141).** The
  database keeps the location each archived record was written to (account endpoint, logical connection name,
  container) and infrastructure controls where the objects actually are. The new setting
  `Whizbang:Archive:AzureBlob:LocationMismatch` decides what a record pinned elsewhere does after a restore, a storage
  failover or a copy of the database to another environment: `Error` (the default) refuses the read, restore, delete or
  write before any request reaches storage, so the archive stops until the location is repointed; `Warning` and `Info`
  go ahead in the configured location and log the mismatch at that level, and the deletion queue deletes every queued
  object from the configured container; `Ignore` goes ahead without comparing or logging. A location written another
  way is the same location: surrounding whitespace, letter case, a trailing slash on the endpoint and the scheme's
  default port (443 for https, 80 for http) are not a mismatch; another scheme, host, port, path, connection name or
  container is. Migration 553 normalizes the stored locations (merging rows that turn out to be one location, so every
  existing record keeps naming the location it meant), normalizes what the lookups and the repoint are given, and
  normalizes every row written to `wh_archive_locations`, a repoint by hand included. A connection name that is only
  whitespace is refused. **Upgrade:** `Whizbang:Archive:AzureBlob:VerifyLocation` and
  `AzureBlobArchiveOptions.VerifyLocation` are removed, and a configuration that still sets the key fails at startup
  naming its replacement: remove it, and set `LocationMismatch` to `Ignore` where `VerifyLocation` was `false`.
