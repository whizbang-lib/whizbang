---
category: Added
subsection: Work coordination, perspectives & sagas
---
- **A write made under a partition epoch that has moved on lands nowhere, and is reported (#2556).** With ownership by
  map on, a claim carries the epoch at which this instance held each claimed stream's partition
  (`WorkBatch.StreamEpochs`, `WorkBatch.StreamPartitions`), and every write that commits a result names it: outbox
  completions and publish marks, perspective work completions and cursor advances, failures, and handler commits. A
  write whose epoch is no longer its partition's affects no row, and the work stays for the partition's current owner.
  It is never silent: the coordinator counts it on `whizbang.work_coordinator.fenced_writes` (tagged `kind`) and logs
  what was fenced at debug, and a fenced handler commit is returned as `HandlerBatchResult.Fenced`, not as a failure.
  A write that names no epoch, and every write with the switch off, is unchanged. The perspective row-version check
  stays: it protects concurrent edits, the epoch protects ownership. A claim that waits because no valid partition map
  is published is no longer silent either: it sets `WorkBatch.PartitionMapUnavailable`, is counted on
  `whizbang.work_coordinator.partition_map_unavailable`, and is warned once per streak, by both PostgreSQL drivers.
  No worker carries an epoch: the work coordinator records each claim's tenures and each fetched piece of work in one
  ledger per process (`PartitionTenures`) and names the epoch on every write itself, a failure reported on its own
  included (migration 572). A perspective row is fenced as well: the set-based and write-behind sink reports a stale
  write `PerspectiveWriteStatus.Fenced` and writes the rest, the per-pair upsert throws `PartitionOwnershipLostException`
  before writing, and a write-behind model whose flush is fenced is dropped. The perspective fence is in the statement
  that writes the row: it holds the row's partition at its claimed epoch until the write commits, so a takeover cannot
  land between a check and the write, and it costs no extra round trip. A perspective write is fenced by the work in
  flight on its stream, so once that work ends (completed, failed, or dropped with the ledger's oldest entries) a later
  write of the stream, such as a local rebuild after its partition moved, is not. Every other fenced write (completions,
  publish marks, cursor advances, failures and handler commits) holds its partitions the same way within its statement,
  in partition order, and the Entity Framework write path opens its own transaction around the hold and the write when
  the caller has none. Migrations 570, 572, 577 and 580. **Upgrade:** `IWorkCoordinator` gains epoch-taking overloads of `CompleteOutboxPublishedAsync` and
  `CompletePerspectiveAsync` whose default implementations ignore the epochs, so a custom coordinator is unaffected;
  `HandlerBatchResult` gains an optional `Fenced`.
