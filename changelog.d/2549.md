- **A stream id that is not a UUIDv7 and reaches a service only through its inbox is now reported (#2549).** The
  stream id check (#2528) ran only where the message's .NET type was known, at event store appends and the dispatcher's
  outbox path, so a remote producer's non-v7 stream id written straight to the inbox was never seen. The EF Core and
  Dapper inbox writes now report it once per stream, with the stream id, the message type name and the entry point,
  and count it in `whizbang.guid_ordering.non_v7_stream_ids`. With `StreamIdOrderingViolationSeverity` set to `Error`
  the inbox write is refused before any SQL runs, so nothing of the batch is stored. The message type is resolved from
  its stored name through the names the generated JSON contexts register, so a stream id declared with
  `[WhizbangId(AcceptAnyVersion = true)]` is still never reported; a name that does not resolve is reported.
  **Upgrade:** nothing to change. A service that raised stream ids to `Error` now also refuses such messages at the
  inbox.
