- **A join or leave moves about 1/N of the partitions, once membership settles (#2558).** The published partition
  assignment now carries an explicit map of the 10,000 partitions to its members, and every claim reads it. The
  elected assigner changes the map incrementally: a joining instance takes about 1/(N+1) of the partitions, evenly
  from the others; a leaving instance's partitions are spread evenly over the rest; nothing else moves. Before, every
  join or leave moved nearly all partitions. Membership changes are collected for a settle window
  (`Whizbang:Database:PartitionAssigner:SettleWindow`, default 5 seconds) before one map is published, so a rolling
  deploy moves a little per instance instead of reshuffling on every heartbeat. A new assigner continues from the
  published map, and an instance is given partitions only once its startup reports ready. The assigner's other
  options (`Enabled`, `AssignmentLease`, `RepublishInterval`) now bind from the same section. Migration 565.
  **Upgrade:** an implementation of `IPartitionAssignmentStore` takes a `PartitionMap` in `PublishAsync` where it took
  the member list (`map.Members` is that list), and `PartitionAssigner.Evaluate` takes how long the membership has
  been unsettled. During a rolling deploy, instances of the previous release publish without a map and the claims
  then rank by modulo exactly as before.
