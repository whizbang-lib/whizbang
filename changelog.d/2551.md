---
category: Changed
subsection: Storage
---
- **A stream's events are versioned in the order they were emitted or the origin wrote them, never by id (#2551).** An
  id is time-ordered and never a stream position, and since #2520 and #2543 an id derived inside a handling sorts at its
  cause, so an effect could sort ahead of the event that caused it. The event store numbered a batch's events per
  stream by id, so a cause and its effect stored together took their versions the wrong way round. Now a stored batch
  is versioned in emission order (its position in the batch the producer stores), the outbox strategies flush a stream
  in the order its messages were appended instead of sorting them by id, "after a terminal event" and "the first event
  decides the stream's kind" are judged by emission position, and a received stream is versioned in its origin's order
  (each origin by the commit sequence it carries, dealt into its arrival slots, as a replay folds it), as is the
  straggler that flags a perspective cursor for rewind. Only a received event that carries no origin position still
  falls back to its id, placed among its origin's events the way a replay places it. The live paths follow the same
  rule: the inbox fetch ranks a stream's received events by stored version and its commands by arrival (a new
  `wh_inbox.arrival_position`), and returns the rank as `InboxBatchRow.StreamPosition`; the perspective read returns
  each event's version (`StreamEventData.Version`, carried onto the envelope's `LocalStreamVersion`); and no worker or
  runner re-sorts a stream by message id any more, ordering it through `StreamOrder` instead. Stored perspective work
  is judged late against its cursor by stream version too (migration 578). The outbox drains in emission order too
  (migration 579): each row takes its emission position as it is stored, and the claim's run, the fetch, the
  continuation and the release of a failed row's run follow it, so the drain publishes a stream in the order it was
  emitted and its continuation cursor is the last position published (`OutboxBatchRow.StreamPosition`,
  `OutboxStreamCursor.LastPublishedPosition`). **Upgrade:** the public
  `MessageOrderingExtensions` (`OrderByMessageId`) is removed; order a stream with `StreamOrder.InStreamOrder`, or keep
  the order the read returned. Streams already stored keep their versions; a stream written after the upgrade by a
  producer still on the previous version is versioned in the order its batches are listed, and the inbox rows already
  queued keep the order they were dispatched in until now. Outbox rows already queued take emission positions in the
  order they were drained in until now. A custom `IWorkCoordinator` that implements `ContinueOutboxStreamsAsync`
  continues a stream after `OutboxStreamCursor.LastPublishedPosition`, and fills `OutboxBatchRow.StreamPosition` on the
  rows it fetches; the drain publishes rows without one in the order they are returned.
