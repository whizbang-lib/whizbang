---
category: Changed
subsection: Messaging & delivery
---
- **An event a receptor publishes explicitly, and the stream a `[GenerateStreamId]` message starts, now take ids
  derived from what caused them (#2520).** Inside a receptor's handling, `IDispatcher.PublishAsync` (both overloads)
  derives the event's id from the handling exactly as an event the receptor returns has since emission identity: from
  the handled message, the service, the handler, the event type and the ordinal of the emission within the handling,
  which returned and published events now share. A `[GenerateStreamId]` message, returned or published, starts a
  stream whose id derives from the message's own id (`GeneratedStreamIdentity`): it sorts with that message and stays a
  version 7 id. A retry of the handling (a lapsed lease, a completion that never committed, a repair that re-runs a
  receptor) therefore re-derives every id, the stored copies of the first run absorb the second run's, and no second
  stream is started. Before, each run published again to every subscriber and started a new stream. A publish outside
  any receptor (an API endpoint, a background service) still mints a fresh id. **Upgrade:** nothing to change. An event
  published inside a handling now carries the handled message's time in its id, as a returned event always has, so
  ordering such events by id orders them by their cause; order a stream by its version. A handling whose first run
  happened before the upgrade and is retried after it publishes once more, as before.
