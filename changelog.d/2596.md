---
category: Changed
subsection: Startup
---
- **Heavy startup work is capped across the fleet, and shared work runs once per schema per build, on both Postgres
  drivers (#2596).** Each unit of work the Converge stage runs on every start is declared with a scope: the perspective
  registry check and the perspective storage settings change state the whole schema shares (`PerSchemaPerBuild`), the
  managed-object reconcile and the analyze of newly indexed tables are per instance (`PerInstance`). The first start of
  a build runs the shared work and records it in `wh_startup_work` (migration 630); every other start of that build skips
  it while a live instance runs it and after it finished. A run that fails or leaves something behind releases its
  claim, so the next start runs it again; a claimer that is no longer live is taken over; another build (a rollback
  included) runs it again, and so does a start whose own schema pass applied anything. While any of its heavy work
  runs, an instance holds one of `MaxConcurrentHeavyStarts` heavy-start permits (default 2, per schema; a permit of an
  instance no longer live is free). Past the cap a start waits in Converge, saying "waiting for a heavy-start permit (N
  of N held across the fleet)", and after `PermitWaitLimit` (default 5 minutes) runs without a permit at Warning. All
  three options bind from `Whizbang:Database:StartupWork` (`MaxConcurrentHeavyStarts`, `PermitPollInterval` default 1
  second, `PermitWaitLimit`). An older release neither takes permits nor reads the record, and runs as before; a newer
  instance on a schema without the functions runs uncapped. **Upgrade:** nothing to change. A storage setting changed by
  hand on a perspective table is now brought back in line by the first start of the next build, not at every restart;
  raise `MaxConcurrentHeavyStarts` if a large fleet should start faster.
