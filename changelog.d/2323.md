category: Changed
subsection: Storage
---
- **Stored event metadata no longer repeats the event id and the scope its row already holds (#2323).** A slim row
  leaves out its message id when it equals the row's `event_id`, and its hop scope when that scope is the row's `scope`
  column and nothing more; every read path of both stores rebuilds them from the row, so an event reads back exactly as
  before, and rows written before and after this release coexist. A message id other than the event id, a hop scope
  carrying roles, claims or principals, and full rows are kept as written. The write paths start trimming only once
  every live instance of the service reads trimmed rows: each heartbeat records `stored_form_level` in its instance
  row's metadata, and the new `metadata-trim-gate` maintenance step latches `wh_settings`
  `metadata_trim_row_values` once every live instance records it. Until then rows keep the form an earlier release
  reads, so a rolling update never hands an older instance a row it cannot read. History conversion follows the same
  gate and trims the earlier slim rows once it opens; the trace store's answers put both values back. No digest
  changes. `EnvelopeMetadata.MessageId` is no longer `required`, `EnvelopeMetadata.MessageIdOf(metadata, eventId)`
  returns a stored event's message id, and `HeartbeatRequest.MetadataJson()` is the heartbeat's metadata with the
  marker. Migration 537. **Upgrade:** nothing to do. The gate is one-way: once it has opened, rolling the library back
  below this release, or starting an instance of an earlier release against the same database, is not supported.
