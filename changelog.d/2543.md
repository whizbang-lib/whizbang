---
category: Changed
subsection: Context, identity & serialization
---
- **Every dispatch path inside a receptor's handling now derives its message ids from the handling (#2543).** Before,
  only explicit publishes (#2520) and returned events did; `SendAsync`, the `LocalInvokeAsync` and
  `LocalInvokeWithReceiptAsync` overloads, `SendManyAsync`, `LocalSendManyAsync`, `PublishManyAsync`,
  `LocalInvokeManyAsync`, a publish routed to local receptors only, and `CascadeMessageAsync` with no source envelope
  minted a fresh id even when called from a receptor body. A redelivered handling (a lapsed lease, a completion that
  never committed) therefore sent its commands again under new ids, which every receiver took for new messages. Now an
  event takes the handling's emission ordinals (`EmissionIdentity`), and any other message, such as a command, takes
  ordinals of its own (`SentMessageIdentity`, prefix `whizbang.sent-message.in-handling.v1`), so sending a command does
  not change the ids of the events the handling returns or publishes. A batch derives one id per item, by the item's
  position in the handling, so the same batch on a redelivery gets the same ids. Outside a receptor (an API endpoint, a
  background service) every id is still a fresh UUIDv7. **Upgrade:** nothing to change in code. A handling whose first
  run happened before the upgrade and is redelivered after it sends once more under new ids, as before. A handling
  that publishes an event to its local receptors only, or cascades with no source envelope, now takes an emission
  ordinal for it, so the events it emits after that derive different ids than on the previous version for a handling
  redelivered across the deploy.
