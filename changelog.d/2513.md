---
category: Changed
subsection: Rebuilds
---
- **A perspective rebuild reads and records its streams a batch at a time (#2513).** Every rebuild mode (in place,
  blue-green, named streams, and the blue-green catch-up passes) now reads the events of up to
  `Whizbang:Perspectives:Rebuild:StreamReadBatchSize` streams (default 100) with one statement, and makes each read
  beside them once per batch: the rows it re-derives, the purge markers of the missing ones and the commit sequences
  of their events (through the registered `IPerspectiveStateSource`), and the cursor write of each flush (migration
  556, `wh_complete_rebuilt_cursors`, used by both drivers' rebuild cursor completers). A blue-green rebuild's
  statement count therefore grows with its batches, not its streams; a rebuild in place still writes each row with
  its own statement. Each stream is folded exactly as before: the same per-stream order (stream version, then the
  origin's order for received events), checkpoints, counts and progress, and a row that moves under its write is read
  again on its own. A stream with archived data still reads its own events through the archive, and a store that
  cannot read a batch (for example when an upcaster changes an event's type) falls back to one read per stream. Set
  the key to 1 to read each stream on its own. `IPerspectiveRunner` gains `ReadRebuildEventsAsync` and
  `RunRebuildWithEventsAsync`, both with defaults, so a hand-written runner keeps working unchanged.
