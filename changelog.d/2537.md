---
category: Changed
subsection: Context, identity & serialization
---
- **A `[GenerateStreamId]` command sent inside a receptor's handling now starts a stream derived from that handling
  (#2537).** `SendAsync` and the local-invoke paths, called from a receptor body, give a `[GenerateStreamId]` command
  (any message that is not an event) a stream id derived from the handled message, the service, the handler, the
  command type and the command's position among the streams the handling starts this way
  (`GeneratedStreamIdentity.DeriveInHandling`). It sorts with the handled message and stays a version 7 id. A
  redelivered handling (a lapsed lease, a completion that never committed) therefore sends its commands on the streams
  its first run started instead of starting new ones that nothing else refers to. One send keeps one stream however
  often the send path generates it, so a stored copy and its local run name the same stream. These ordinals are the
  handling's own: sending a command does not change the ids of the events the handling returns or publishes. The
  command's own message id is still minted, and a send outside any receptor (an API endpoint, a background service)
  still mints a fresh stream. **Upgrade:** nothing to change. A handling whose first run happened before the upgrade
  and is redelivered after it starts one more stream, as before.
