- **A fan-out row comes out live as its rebuild does when its own events and the foreign events interleave (#2622).**
  The collective sink and a row's runner apply independently, so a rename can land before or after an order's own
  events. A live batch of a row a fan-out targets now folds again each foreign event the sink has already applied
  that was committed after one of the batch's events (a rename applied before `OrderPlaced` was folded, or before an
  older event that would overwrite it), and leaves one the sink has not applied yet to the sink. After each fan-out it
  applies, the sink rewinds every targeted row that had already folded a newer event of its own, from that row's first
  event after the foreign one (`wh_rewind_fan_out_rows_applied_late`, migration 760, found by the key's index). A model
  with no fan-out does none of this. One window is still open: an update that misses a row whose key is written a
  moment later, while the row's read missed the update, leaves that row without the event until its next rewind or
  rebuild.
